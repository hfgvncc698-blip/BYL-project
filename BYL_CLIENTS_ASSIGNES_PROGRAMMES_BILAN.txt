Annulation HTTP : les tâches non lancées sont interrompues ; les lectures déjà envoyées à Firestore ne sont pas annulables. Les réponses obsolètes sont rejetées côté page. Une réponse incomplète ne devient jamais un compteur nul.
404 uniquement : compatibilité avec une ancienne API via le chemin SDK. Pas de répétition automatique des scans après 401/403/503. Une panne du nouvel endpoint laisse les compteurs non confirmés ; elle nécessite une nouvelle tentative, plutôt que doubler les lectures.

COMMENT INTERPRÉTER LE COÛT
Ne pas confondre docs retournés, opérations SDK et lectures facturables. Les wrappers ne voient pas les get()/exists() des règles. Les tableaux ci-dessus isolent ces lectures explicites et leur estimation complémentaire.
Pour un coach autorisé, chaque requête SDK de l’annuaire ou des programmes doit consulter le profil via currentUser()/hasCoachAccess(). On compte prudemment une seule lecture de profil par requête (N + 3) ; les lectures du dossier parent dans la règle programmes ne sont même pas ajoutées à ce minimum. Les dépendances identiques ne sont comptées qu’une fois par requête.
Documentation primaire : https://firebase.google.com/docs/firestore/pricing — section sur les lectures additionnelles nécessaires aux règles de sécurité. Firebase précise leur facturation par requête, avec une seule lecture par document dépendant même si plusieurs appels le consultent.
Après regroupement, le SDK Admin n’exécute pas les règles navigateur : les contrôles sont explicitement implémentés et comptés dans la route. Le total documenté est donc une estimation facturable basée sur les règles actuelles et les traces de requêtes, PAS une facture réelle ni une mesure directe de toutes les dépendances.
Les écritures de session du banc (1 côté navigateur) et les lectures communes des modèles/messagerie ne changent pas et ne sont pas attribuées à cette optimisation. Aucun service Google nouveau, index ou tâche automatique ajouté. Ressources CPU/mémoire du VPS sous charge, facturation réseau et prix en euros non qualifiés ici.
Le SDK backend fait désormais une partie du travail : ne pas prétendre que les lectures ont été supprimées. Le gain documentaire estimé vient des contrôles de règles répétés évités, sans supprimer les contrôles serveur.

LIMITES ET RISQUES RÉSIDUELS
Les critères de durée sont démontrés sur réseau local et fixtures, pas sur un compte réel, réseau mobile, ni en concurrence de nombreux coachs. Le scan serveur canonique reste proportionnel au nombre de dossiers ; 600 dossiers maximum comme les trois anciennes limites de 200.
Les compteurs de racine indiquant zéro programme continuent d’être respectés comme avant : leur qualité historique n’est pas corrigée dans ce lot. Les anciens formats incomplets peuvent avoir les mêmes limitations qu’avant.
Les erreurs réseau/transactions relancées peuvent coûter davantage que le chemin nominal ; aucun invariant absolu sur la facture lors de toutes les pannes n’est affirmé. Les mécanismes existants de réconciliation Auth peuvent écrire un marqueur lors d’un rejet Auth : ce sont des opérations de sécurité exceptionnelles, pas des écritures de résumé.
La comparaison ne constitue pas une validation des risques P0-3/P0-4 existants. Aucune règle de production modifiée.
