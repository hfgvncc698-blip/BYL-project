13 novembre 2026 — codex/firebase-performance-audit — aucun déploiement

Décision utilisateur : coût total inférieur recherché, coût initial mesuré accepté.
Résultat : gain de délai démontré sur le cas réel ; cible de 2 s pour tout le
Dashboard non atteinte. Économie monétaire globale non démontrée : la solution

1. CAUSE ET CORRECTION
Les prescriptions complètes (exercices, médias et descriptions) dominaient la
lecture Firestore et le transport, alors que le Dashboard n'utilise qu'une partie
de ces champs. Sur le second lot de 31 dossiers réel, les prescriptions
représentaient 13 908 889 octets JSON ; les historiques 752 716 octets.

Le Dashboard reçoit maintenant une projection conservant les champs nécessaires
aux calculs de progression, titres, durées, reprise et décisions Copilot. Les
historiques canoniques restent interrogés : aucune approximation des compteurs.
ProgramView/SessionPlayer chargent les détails complets via leurs parcours
existants. Une projection ne doit jamais remplacer le document canonique.

Le backend conserve les projections en mémoire, dans un cache limité à 32 Mio de
JSON (ce n'est pas une limite de RSS). Chaque réutilisation exige les contrôles
d'autorisation actuels et une lecture des métadonnées Firestore : projet, chemin
et updateTime exact doivent correspondre. Une modification externe ou ancienne
change cette version ; une suppression retire le programme des résultats.
Pas de document de synthèse persistant, de nouvel écouteur ni de tâche planifiée.
Durée de réutilisation maximale : 24 h. Redémarrage, éviction ou nouvelle version
peuvent refaire payer la lecture initiale. Chaque instance possède son cache.

Les lectures restent bornées à 32 simultanées par requête ; le premier groupe de
clients visibles reste prioritaire. L'ajustement Copilot relit le document entier
dans une transaction, vérifie que la séance examinée n'a pas changé, puis applique
la correction à la source complète. Images/champs inconnus sont préservés. Une
réponse tardive après fermeture de session n'actualise pas l'interface. Le code
d'ajustement est importé à la demande pour respecter le budget JavaScript.

4. COÛTS ET CONDITIONS
Un cache vide ajoute une lecture complète par programme après sa projection de
métadonnées. Une consultation avec cache valide garde le nombre de documents lus
mais réduit leur taille transférée. Les historiques restent lus. Une modification
Copilot ajoute normalement une lecture transactionnelle à son écriture existante ;
les retries peuvent en ajouter. Aucun nouveau service Google, aucune écriture de
résumé et aucun stockage Firestore supplémentaire.

Seuil économique à qualifier : coût des lectures initiales/évictions/actions
comparé au coût du trafic évité sur les consultations répétées. Ce seuil dépend
de la région, du trafic réellement facturable, des quotas et du nombre d'instances.
Si le trafic était gratuit, la baisse de volume peut ne pas compenser les lectures
supplémentaires. Le coût total inférieur demandé n'est donc pas encore prouvé.
Ne pas convertir ces estimations en économie de facture ou montant exact.
Documentation : https://firebase.google.com/docs/firestore/pricing
Le nombre de lectures facturées et le trafic sont des postes distincts.

6. ESSAIS ÉCARTÉS ET LIMITES
La mise en parallèle des deux lots pénalisait les clients récents : retirée.
La déduplication des chaînes/objets gagnait beaucoup sur médias synthétiques mais
peu sur le réel : retirée du code actif, conservée sous audits/dashboard-shared-text
pour traçabilité. Un premier build dépassait le budget du chunk Dashboard ; la
mise à la demande du code d'ajustement a corrigé cet échec sans relever le budget.

Le premier passage après redémarrage reste ~14 s. Les historiques représentent
encore ~0,75 Mo pour les 31 derniers dossiers et sont relus pour leur exactitude.
La cible globale <2 s et la baisse monétaire ne sont pas acquises. Les anciens
clients API gardent leur format historique. Les entrées expirées non réutilisées
peuvent rester en mémoire jusqu'à éviction ; aucune garantie d'effacement physique.
Aucun nettoyage de cache utilisateur, migration ou déploiement réalisé.
